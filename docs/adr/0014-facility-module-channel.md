# ADR 0014: 시설 모듈과 Core 사이의 통로 — 파일 두 개

상태: 채택·Core 구현·실행 검증(2026-11-20). 개발 VM에 Live Fire 모듈 `m4-facility`를 설치해 화면에서 장애 주입 → 통로 온도 상승 → 경보 → 자동 복구 → 감사 기록을 확인했다. 첫 설치에서 요청 볼륨의 소유자가 모듈 이미지의 것으로 바뀌는 결함을 찾아 고쳤다(설치기가 볼륨에 표시 파일 `.core`를 둔다. Docker는 빈 볼륨을 처음 붙일 때 이미지 디렉터리의 소유자를 복사한다).

- 잇는 것: [ADR 0010](0010-facility-display-and-network-devices.md)의 "M4는 시설 상태를 정해진 스키마로 Core에
  넘긴다"와 "학생은 자기 Core의 M4 화면에서 주입한다". 그 문서가 미뤄 둔 스키마와 전달 방법을 정한다.
- 바꾸지 않는 것: 시설 물리 계산과 장애는 M4(Live Fire)의 일이다. Core는 계산하지 않고 장애를 만들지 않는다.

## 배경

Core의 모듈 Compose 계약은 읽기 전용·비 root·권한 없음이고, 모듈과 Core 관리 화면(platform)은 같은 망에
있지 않다(platform은 내부망, 모듈은 사용자망). 지금까지 모듈이 Core에 데이터를 주는 길은 C1 활동 기록
볼륨뿐이고, Core 화면이 모듈에 요청하는 길은 없었다. 이전 인프라의 시뮬레이터는 HTTP API와 Docker 소켓,
조회 문자열의 키로 동작했다. 그대로 옮기면 새 포트·새 망 경로·소켓이 생긴다.

## 결정

1. **능력 `facility-state`.** platform 컴포넌트가 제공하고, 유료 모듈 하나만 가질 수 있다. 관리 화면
   (management)이 없으면 설치를 거절한다.
2. **볼륨 두 개, 방향이 하나씩.**
   - `facility-state` → 모듈이 `/run/xoc-facility/state.json`을 쓴다(원자적 교체). platform은 읽기 전용.
   - `facility-requests` → platform이 `/run/xoc-facility-requests/<요청 ID>.json`을 쓴다. 모듈은 읽기 전용.
   - 망 경로·포트·소켓·공유 비밀이 없다. 각 볼륨은 쓰는 쪽 소유다(설치기가 맞춘다).
3. **계약.** `xoc.facility-state/0.1.0`(`contracts/facility-state.json`)과 `xoc.facility-request/0.1.0`
   (`contracts/facility-request.json`). 상태에는 요약·설비별 상태와 측정값·통로 온도·경보·진행 중인 장애·
   넣을 수 있는 장애 목록·부하 묶음·처리한 요청·기록이 있다. 정답·채점·힌트 필드는 없다.
4. **Core는 받은 문서를 항목별로 다시 확인한다.** 계약 밖의 값이 하나라도 있으면 문서 전체를 버린다
   (`<`·`>`·제어 문자 금지, 길이·개수 상한). 30초 넘게 갱신되지 않은 상태는 실시간으로 표시하지 않는다.
   모듈이 없거나, 라이선스가 없거나, 상태가 없으면 지금처럼 기준값("시뮬레이터 없음")을 보여 준다.
5. **요청.** `POST /core/api/facility/requests`. 운영자·관리자만, 요청마다 라이선스를 다시 확인한다(만료면
   조회만). 종류는 `inject`·`clear`·`clear_all`·`shed`·`restore`·`time_scale`뿐이다. Core는 형식만 확인해
   파일로 넘기고, 받아들일지는 모듈이 정해 상태의 `handled`로 알린다. 요청은 감사 기록에 남는다
   (`facility_<종류>`). 처리된 요청과 10분 넘은 요청 파일은 Core가 지운다. 대기 64개를 넘으면 거절한다.
6. **화면.** 모듈은 C4로 자기 경로(`/core/#module/<모듈 ID>`)를 등록한다. Core는 그 모듈이 이 능력을 가졌으면
   그 경로에 시설 운영 화면을 그린다. 데이터센터의 B1·옥외 시설 보기는 실시간 값과 상태를 함께 보여 준다.

## 검토한 다른 방법

- 모듈의 HTTP API를 platform이 호출: 새 망 경로와 인증이 필요하고, 모듈이 임의 응답으로 화면을 흔들 수 있다.
- C1 이벤트로 상태 전달: C1은 사건 기록이지 현재 상태가 아니다. 5초마다 전체 상태를 넣으면 SIEM 저장소를 채운다.
- Core가 시뮬레이터를 실행: Core 경계(ADR 0001, 0010) 위반.

## 추가(2026-11-20): 시설 사건을 SIEM으로

현재 상태는 위의 상태 파일로, **일어난 일**(경보 발생·해제, 장애 넣기·되돌리기·자동 복구, 운영 조작)은 C1로
보낸다. 모듈이 같은 상태 볼륨의 `events.jsonl`에 한 줄씩 쓰고, 호스트 수집기가 수집원 `facility-events`로 읽어
C1 v0.4(`xoc-facility`)로 정규화한다. 새 볼륨이나 망 경로는 없다. 형식과 규칙은
[C1 문서](../contracts/C1-EVENT.md)의 v0.4 절에 있다.

## 추가(2026-11-20): 반 전체 장애를 받기 위한 자격 증명

ADR 0010 4항("강사의 반 전체 주입은 Range Control을 거친다")을 위해, 시설 상태를 맡은 모듈은 증거 조회
모듈과 같은 읽기 전용 자격 증명 볼륨(`module-<모듈>-credentials` → `/run/xoc-module`, ADR 0008)을 받는다.
모듈은 그 인증서로 학교 Range Control에 **밖으로만** 접속해 장애 과제를 받아 온다(받는 포트 없음).
`xoc module credentials <모듈> --from <디렉터리>`가 이 모듈에도 동작한다. Core와 모듈 사이의 통로는
여전히 위의 두 볼륨뿐이다. Core는 장애 과제의 내용을 알지 못한다.

## 남은 것

- 실제 컨테이너에 영향을 주는 IT 장애는 이 통로로 하지 않는다. 별도 결정이 필요하다.

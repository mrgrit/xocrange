# ADR 0011: Live Fire 학생 도메인 — 설치 때 중앙 서버를 찾으면 학생이 정한 내부 도메인, 못 찾으면 Core만

- 상태: 소유자 결정, 2026-11-16 (허용 접미사 4종, hosts 목록은 반 전체)
- 관계: 정본 `xocrange_plan` TIERS의 "도메인: Community는 `xoc.range`를 hosts로만, Live Fire는 사용자 도메인·TLS"를 구현하는 방법을 정한다. Live Fire L15 중앙 DNS(`<이름>.lf.range`)를 대체한다.

## 배경

- Core는 실습 타깃을 `<타깃>.xoc.range`로만 연다(`components/security-path/web/start.py`의 웹 입구 설정, 인증서 이름 `xoc.range`·`*.xoc.range`). 모든 Core가 같은 이름이라 중앙 DNS에 넣을 수 없고, 학생 PC의 hosts 파일로 자기 Core에만 잇는다. Community는 이대로 둔다(브랜드 유지).
- Live Fire L15는 학생이 `<이름>.lf.range`를 등록하면 그 Core 주소로 해석해 준다. 하지만 Core 웹 입구가 그 이름을 모르기 때문에 관리 화면으로 떨어지고 인증서 이름도 맞지 않는다. L12 대전은 IP에 `Host: dvwa.xoc.range` 헤더를 붙여 공격했다.
- kt66은 설치할 때 내부 도메인을 한 번 묻고(기본 `kt66.lab`), 서비스를 그 아래에 둔다(`dvwa.<도메인>`, `siem.<도메인>`, `mail.<도메인>`). 웹 입구 설정과 인증서를 그 도메인으로 다시 만들고, 실습 DNS(컨테이너용·강의실 PC용)와 hosts 블록을 생성한다.
- Core는 무료와 Live Fire가 같은 설치 프로그램이다. 도메인 입력을 그냥 넣으면 무료 설치도 Live Fire 기능을 쓰게 된다.

## 결정

1. **설치 분기.** `install.sh`가 같은 서브넷에서 Live Fire 중앙 서버(Range Control)를 찾는다.
   - 찾으면: 강사가 알려 준 **반 등록 코드**를 묻는다. 중앙 서버는 코드와 구매 라이선스(Live Fire 이상, 좌석)를 확인한다. 그다음 학생이 도메인을 입력하면 중앙 서버가 규칙과 중복을 검사하고, 이 레인지의 등록과 C7 라이선스(기관·레인지·**도메인**을 서명)를 발급한다. 설치는 그 도메인으로 진행한다.
   - 못 찾거나 코드가 없으면: "Live Fire 서버를 찾을 수 없습니다. Core만 설치합니다." 그리고 Community(`xoc.range`)로 설치한다.
   - 찾는 방법: 중앙 서버가 고정 UDP 포트의 브로드캐스트 질의에 자기 주소와 CA 지문을 답한다. 같은 망의 가짜 서버는 등록 코드를 검증할 수 없으므로(코드는 중앙 서버만 아는 비밀로 확인) 거기서 멈춘다. 자동 탐색이 막힌 망에서는 `--livefire <주소>`로 직접 준다.
2. **도메인 형식(kt66과 같음).** 학생이 정하는 내부 도메인 하나(예: `alice.lab`) 아래에 서비스를 둔다: `dvwa.alice.lab`, `juiceshop.alice.lab`, `siem.alice.lab`, `alice.lab`(입구).
   - 실제 공개 도메인과 겹치지 않게 허용 접미사 목록 안에서만 받는다. 기본 목록은 `.lab`, `.test`, `.internal`, `.home.arpa`이고, 학교가 Range Control에서 바꿀 수 있다.
   - 중복은 중앙 서버가 반 안에서 막는다.
3. **이름은 내부에서만, hosts로 자동 배포.** 중앙 서버가 반의 도메인 목록(도메인 → 그 Core 주소)을 가진다.
   - 각 Core 호스트: 등록된 Core에만 설치되는 root 타이머(`xocrange-livefire-hosts`, 2분 간격)가 레인지 인증서로 나가는 연결을 열어 목록을 받는다. `/etc/hosts`의 관리 블록(`# BEGIN XOC LAB DOMAINS` … `# END`)만 갱신하고 다른 hosts 항목은 건드리지 않는다. 연결이 안 되면 기존 블록을 그대로 둔다.
   - 공격자 VM: 공격자 에이전트가 이미 쓰는 나가는 연결로 같은 목록을 받아 같은 블록을 갱신한다(1분 간격).
   - 실습 이름(.lab 등)과 사설 IPv4만 쓴다.
   - 학생 PC: Range Control 화면에서 자기 반의 hosts 블록을 내려받는다. hosts를 고치기 어려운 PC를 위해 중앙 서버의 실습 DNS가 같은 목록을 제공하는 것도 선택으로 둔다.
   - 그래서 학생은 다른 학생 시스템을 도메인 이름으로 공격할 수 있다(`dvwa.bob.lab`). 목록 범위는 반 전체(코호트)다.
4. **Core 웹 입구와 TLS.** 서명된 Live Fire 라이선스에 도메인이 있고 유효할 때만, Core 웹 입구가 `<타깃>.<도메인>` 이름을 더 받고 Core CA로 `<도메인>`·`*.<도메인>` 인증서를 만든다. 라이선스가 없으면 `xoc.range`만 쓴다. 만료되면 유예 기간(제안: 14일) 뒤 `xoc.range`로 돌아간다. `xoc.range` 이름은 Live Fire에서도 계속 동작한다.
5. **Core CA 이름 제한.** 학생 PC가 신뢰하는 Core CA가 실제 사이트 인증서를 만들 수 없도록, CA에 이름 제한(Name Constraints)을 건다. 허용 범위는 `xoc.range`와 허용 접미사 목록이다. 이 개선은 Community에도 적용한다(새 CA부터, 기존 설치는 CA 재발급 안내).
6. **경계.**
   - 설치 분기·등록 요청·라이선스에 따른 웹 입구 이름 추가는 Core에 둔다. Core에는 유료 기능 자체가 들어가지 않고, C7 승인으로만 켜진다.
   - hosts 목록 동기화는 등록된 Core에만 생기는 호스트 타이머와 공격자 에이전트가 맡는다. 컨테이너인 판정기 모듈은 호스트의 `/etc/hosts`를 쓸 수 없기 때문이다. 동기화에 채점·판정 기능은 없다.
   - Core에 새로 열리는 포트는 없다.

7. **위임 발급(C7 계약 0.2).** 지금 키는 공급사가 레인지마다 서명하므로, 학교 중앙 서버가 설치 순간에 학생 레인지 키를 만들 수 없다.
   - 공급사는 학교 Range Control에 **발급자 인증서**(`xoc.issuer/0.1.0`)를 서명해 준다. 인증서에는 발급자 공개키·기관·최고 등급·모듈 범위·좌석 수·유효 기간이 들어간다.
   - Range Control은 그 범위 안에서 레인지 키(`xoc.entitlement/0.2.0`)를 서명한다. 레인지 키에는 기관·레인지·도메인과 발급자 인증서가 들어간다.
   - Core는 "공급사 공개키 → 발급자 인증서 → 레인지 키" 사슬을 확인한다. 기관이 같아야 하고, 등급과 모듈은 발급자 범위 안이어야 하며, 기간도 발급자 기간 안이어야 한다.
   - 좌석 수는 Range Control의 발급 대장에서 센다. Core는 셀 수 없다.
   - 공급사가 레인지마다 직접 서명한 0.1.0 키도 계속 받는다.

## 결과

- Community 설치는 바뀌지 않는다(중앙 서버가 없으면 지금과 같다).
- L15의 `<이름>.lf.range` 등록은 이 방식으로 대체한다(중앙 DNS는 선택 기능으로 남긴다).
- 남은 결정:
  - 유예 기간(제안 14일)
  - 기존 L15 등록의 이전 방법
